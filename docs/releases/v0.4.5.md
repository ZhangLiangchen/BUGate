# BUGate v0.4.5

[English](v0.4.5.md) | [简体中文](v0.4.5.zh-CN.md)

Status: source release notes for the v0.4.5 minor release. This file does not
by itself prove tag creation, CI completion, asset publication, or
public-download reacceptance; those remain release-operation gates.

BUGate v0.4.5 adds governed test-asset self-healing: a route from "this failure
is a broken test asset" to a reviewed, evidence-bound repair, anchored in a
sidecar rather than in the frozen role-evidence chain. The feature is **off by
default** and its authorization boundary is deliberately narrow.

## Failure attribution and the self-healing sidecar

The post-run layer could classify a failure but not attribute one. `PATTERNS`
matched bare substrings with no word boundaries, so a debug line about a pooled
connection was enough to pin `sut_defect_admissible` to `False`. The release
adds anchored attribution (`failure_owner`, `failure_subtype`) with explicit
counter-examples; ambiguous evidence returns `insufficient_evidence` with
`healing_eligible: false` and never guesses an owner.

Repairs are governed through a six-event sidecar under
`<artifact_dir>/00_self_healing/`: triage, handoff, accept, propose, bound
independent review, close. The sidecar exists because the main role-evidence
chain is frozen — a healer acting as implementer during post-run can never be a
legal main-chain actor, and one unknown event written into a UC's main chain
would make every v0.4.0–v0.4.4 engine fail that chain outright. Design record:
[`BUGATE_SELF_HEALING_SIDECAR_ADR.md`](../qa-methodology/BUGATE_SELF_HEALING_SIDECAR_ADR.md)
(ADR-BUGATE-005).

## Off by default, and byte-identical when off

`self_healing.mode` defaults to `off`. A repository that never sets
`self_healing` has exactly the v0.4.4 behavior: `--scope self-heal` returns
`disabled` at exit 0 and creates nothing, and `--scope post-run` output is
byte-identical to v0.4.4 — pinned by golden fixtures captured from the v0.4.4
engine itself. `verify` mode proves a repair in a sandbox copy and never writes
the real tree; only `apply_with_approval` writes back, only after the full
review flow and a human approval record, only to paths the profile's
`allowed_write_regex` names, and only through a journal that records every
target's exact prior bytes before the first write.

## The authorization boundary is narrow, and stated

A dynamic counterexample is only a falsifying observation. Arbitrary Python can
recognize any finite candidate-visible mutant, so a clean dynamic kill is not by
itself proof of honest behavior. Automatic authorization is therefore limited to
two closed, decidable candidate languages: the engine-derived NameError/literal
repair, and the canonical external JSON-evidence assertion. Every other
candidate shape stops at exit 2 — blocked, with nothing written to the workspace
or the sidecar.

Exit 3 ("the repaired test survives a declared oracle violation") is issued only
when the assertion binding is carried by one of those closed *static* proofs. It
is never derived from evidence the candidate under test produced: the engine and
the candidate share one interpreter, and a candidate can read an injected probe
out of its own source before deciding what to print, so no in-band execution
witness can establish that binding. The consequence is stated rather than
hidden — some candidates that really are fake-green are blocked without being
named. The full boundary, including measured authorization rates, is in
[`CAPABILITIES.md`](../../CAPABILITIES.md).

## Verification carried in-repo

The release adds the regression floor for both defects found while reviewing
this feature, plus an exact-one-anchor engine mutation harness
(`tests/test_engine_mutation_guards.py`) that injects exactly one anchored
change into a copy of the engine and requires the single named guard to fail.
Nine mutants cover structural-finding codes, review-manifest binding, the apply
branch, the sidecar transition guard, sidecar integrity reasons, two collateral
write leaks, and both assertion-binding fixes. The harness refuses to inject a
mutation whose anchor is absent or ambiguous, so a no-op injection can never
report as a passing guard.

## Compatibility

`bugate_init.py` remains fresh-install-only. The updater protocol floor remains
v0.4.2. v0.4.3 role-lineage semantics, the `evidence_recovery` event, and the
v0.4.4 `bugate-update` skill and bilingual update prompts are unchanged. No
frozen governed-evidence layout leaf is added; self-heal evidence lands in
`00_self_healing/`, never in `00_role_evidence/`.

## Contract and publication gates

The normal compile, discovery, direct-file, de-SUT, pre-code semantic, and
imported updater regression suites remain mandatory. Formal archive acceptance
must use the exact flags
`--full-check-mode smoke --full-check-archive both` against independently
unpacked tar and zip artifacts.

That smoke workflow retains the v0.4.3 lineage oracle: six lifecycle events plus
one state-preserving `evidence_recovery` receipt, for seven exact anchors.
Semantic release review remains provider-neutral. Cross-provider review is
preferred; if a provider is unavailable, only a newly spawned same-provider
session with an independent prompt and no access to the first conclusion before
synthesis is an acceptable fallback. Placeholder output, a continued session,
self-review, or an outage relabeled as success does not satisfy that gate.

The release distribution must contain exactly:

```text
bugate-0.4.5.tar.gz
bugate-0.4.5.zip
bugate-0.4.5.SHA256SUMS
```

Final SHA-256 values are generated only from the clean merged commit. The
acceptance JSON is evidence, not a public release asset.

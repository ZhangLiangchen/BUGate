# 验收范围与充分证据

[English](ACCEPTANCE_SCOPE.md) | 简体中文

验收范围契约记录本轮采纳的有限目标及其证明方式。它是有版本的协议实体，不是一段建议性提示词。精确字段和规则以 [ScopeContract Schema](../protocol/v2/schemas/scope_contract.schema.json) 和[验收 MethodSpec](../protocol/v2/methods/acceptance_scope.json) 为准，现有 inventory 仍是可执行计划的唯一权威。

默认围绕用户指定目标形成最小充分证据闭环。深度与广度分开：目标包含业务持久化、归属或下游影响时，仅接口成功不充分；新增租户、角色、环境、流程或风险类别则需要明确目标或不可缺少的要求到目标关联。“最佳实践”不能单独提供这个依据。

契约引用请求来源和已有业务要求、Oracle，避免另建计划后重复事实。它表达对象/环境边界、主流程入口/节点/终点、必要分支、必需场景及必要性、排除项、辅助活动边界、完成条件和变更历史。可以是一条流程、多个必要分支、一组有限目标，也可以验收拒绝或失败行为，不限定只能有一条成功路径。

用户明确要求、不可缺少的推导条件、未解决假设和可选建议分别记录。假设会改变验收方向时，保留缺口并提出最小澄清。意图清晰时，无需逐字段反复审批。排除已明确要求的行为属于冲突，不能借此减少覆盖。

## 四类示例

| 用户请求 | 必需范围与观测 | 未明确要求时属于范围外 |
|---|---|---|
| “普通用户可以创建订单。” | 以该用户登录，提交有效订单，通过约定 Oracle 读取订单持久化后的归属和业务字段。 | 跨租户攻击、模糊测试、并发与性能专项。 |
| “普通用户不能替其他租户创建订单。” | 跨租户尝试是必需拒绝分支，观测预期拒绝及未产生越权订单。 | 其他无关漏洞类别。 |
| “验证正常、边界和失败行为。” | 完整保留三类明确要求的场景及各自业务 Oracle；预期拒绝本身可以是通过结果。 | 没有来源和必要性依据的更多变体。 |
| “创建订单”，但真实执行返回错误归属。 | 保留真实失败，完成有界诊断；约定证据齐备时报告执行完成、功能验收失败。 | 为补偿失败或制造全绿而追加测试。 |

第一类示例即使记录了压测、其他浏览器等建议，也不影响完成。报告可以写“验收执行完成；约定要求满足；无执行阻塞；另有两项范围外建议”，同时明确“本结论仅覆盖本次约定范围”并列出范围，不能扩大为产品整体安全或全面正确。

登录、准备数据、读取来源/证据、分析和清理属于辅助活动，不自动成为验收目标。诊断执行必须关联当前失败及声明的有界活动；预算耗尽后保存已知结论或真实阻塞。诊断发现范围内失败时，该失败仍影响验收结果。

## 计划、变更与证明

每个必需用例绑定当前契约版本/摘要、要求、流程/分支、业务 Oracle、预期证据和必要性。静态检查验证引用、版本一致性和范围归属；语义评审另行根据来源判断必要性。字段齐备或模型自报必要性不证明业务正确。

无关发现记录为建议。建议不是执行计划，也不是待完成必测项，不能通过间接依赖阻塞完成。要扩展测试，请在新的用户请求中明确新增目标或类别，例如“另外验证用户不能替其他租户创建订单，沿用当前环境”。锁定 Profile 需求/风险同分母内，用户授权的分支/Oracle 变化产生新契约版本，记录来源与影响并重新评估计划和声明。新增目标改变分母时，`SCOPE_PROFILE_CHANGE_REQUIRED` 引导显式新 Profile 版本及 `init` 新任务；可用新 Profile source 引用旧契约快照，保留原任务与失败。不提供同任务 Profile rebind 或自动迁移。ScopeRequest 证明用户选择，领域证据仍来自 Profile 声明来源。失败、时间压力或执行困难不能授权 Agent 缩减目标。

范围契约不能越过宿主权限或工具安全边界。受管执行依据可观察的用例/活动 ID 和精确当前绑定；BUGate 无法从任意 shell 文本理解所有业务语义。宿主须在可信输入接缝收集用户原始请求，模型写出的批准字符串不具备该来源。同权限操作者控制全部本地文件的恶意修改不属于本地证据真实性保障。

旧范围、计划或快照的评估不能授权新执行或声明。本版本对范围变更采用保守失效策略：全部旧范围/计划执行授权和证据适用性失效；历史证据与失败仍可查看，但必需用例必须重新运行。不提供选择性证据复用，也不因字段未变而恢复旧评估。冷恢复、压缩和子 Agent 均独立准备当前绑定，参见 [DSH 使用与恢复](DEEPSEEK_HARNESS.zh-CN.md)。

## 结果表达

| 执行/证据闭环 | 功能验收 | 必须报告 |
|---|---|---|
| 完成 | 满足 | 实际覆盖要求、真实业务观测和可选建议。 |
| 完成 | 失败 | 真实失败和证据；执行完成不能把失败变成通过。 |
| 未完成 | 未确定 | 缺少的必需执行/证据及真实阻塞，不把模型标记或结构检查当证明。 |
| 完成且有建议 | 满足或失败 | 范围内结论保持不变；建议单列，不自动触发返工。 |

结构化 `AssessmentResult.acceptance` 分开返回 `execution_complete`、`functional_result`、`requirement_ids`、`blocking_codes`、`suggestion_ids`、`historical_failure_ids` 和 `coverage_statement`。执行完成与 `requirement_verified` 仍分别评估。`requirement_verified` 声明可以只指定 R1；此时 `AssessmentResult.scope` 只列该声明实际覆盖的需求，而 `acceptance.requirement_ids` 仍列 Profile 的全部约定要求。R1 验证通过不会使尚未观测 R2 的整体 `execution_complete` 或 `functional_result` 变成通过。

报告明确区分覆盖、功能结果、执行阻塞及范围外建议。确定性 runtime 测试通过不意味着 live-model 质量收益已得到证明。
